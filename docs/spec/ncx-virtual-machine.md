# NCX Virtual Machine

Status: Version 1.0 of the specification set, 2026-09-12 (draft 8 in the drafting history of `../decisions/decisions.md`). Companion to `ncx-language.md`: what every word does to the state of a channel, and what the virtual machine reports.

The virtual machine (VM) is the one component that knows what an NCX program means at every block. Readers use it to resolve what the source controller left implicit, the compiler uses it to know what the target controller needs written, and analytics read it. Nothing about the VM is visible in the NCX text; the text carries only what changes.

## 1. Where the VM sits

```
NC file ──► reader (Fanuc, Heidenhain, Siemens) ──► NCX blocks ──► writer ──► program.ncx
             uses a source-side VM to resolve modal G-codes, incremental values,
             preloaded tools, active cycles

program.ncx ──► parser ──► expander ──► VM ──► compiler (machine TOML) ──► NC file for one machine
program.ncx ──► parser ──► expander ──► VM ──► analytics (text output)
program.ncx ──► parser ──► expander ──► VM ──► kinematics module (optional, section 10)
```

The expander applies the expansion rules of the machine configuration and the program rewriters of the plugins: it inserts generated NCX blocks before or after a block (a spindle stop before the through-spindle coolant, a retract before a tool change, a mode M code before a cycle) and may rewrite words (a speed clamped to the spindle limit). Everything it produces is NCX, so the VM executes it like the rest (3.10). `format` does not run the VM at all: it is the parser and the writer (D91).

Two execution modes:

- **STATIC**: one pass top to bottom over every program of the file. The control flow words `JUMP` and `REPEAT` are recorded, not followed; `CALL` is followed: at every `CALL` the subprogram is walked with the caller's state at that point, so a subprogram is walked as often as it is called (D99). A `CALL` with `TIMES=n` is walked n times in sequence, each time from the state the previous pass left, so the caller continues with the state after the last pass (D99); a `TIMES` from an expression walks the subprogram once with the caller's state, and afterwards every axis whose position that pass changed becomes unknown, while the axes it left where it found them stay known (D136). Every program starts from the initial state of its channel (section 2 Initial column, positions per D100), as the job enters it, the tool in the spindle included; nothing is carried over from the previous program's `PROGRAM=END` (D134). Expressions are not evaluated; a state variable set from an expression becomes UNKNOWN. A subprogram that no program of the file calls is walked once from a default entry state: units, workplane, diameter and feed mode as at the first verb of the file's first program, everything else initial, position unknown (D99). If that program has no verb, they are taken as they stand at its first `CALL`, before entering the callee; if it has no `CALL` either, as they stand when the walk reaches its `PROGRAM=END`, before that block resets the feed mode. A verb in the program's own blocks still wins (D135). A `CALL` of an external program is not followed in STATIC mode: the call is recorded, the state after it is the state before it, and the position becomes unknown (the external program is checked on its own). This is what `convert`, `compile` and `check` use (D91).
- **INTERPRETED**: the program is executed, variables evaluated, jumps and calls followed, with a block cap against endless loops. This is what `analyze` uses by default.

## 2. State

Everything below exists once per channel unless marked "per resource" or "per job". In a job the tool rows of 2.3 that name the tool in the spindle and the preload, and the spindle rows of 2.4, are one per job, read and changed by every channel's VM in round order; the offset and point rows of 2.3 and everything in 2.1, 2.2 and 2.5 to 2.7 stay per channel (2.8, D308).

### 2.9 Diagnostics

`block.index` (1-based line in the file, plus the file name for called programs) and a diagnostics list of (severity, code, file, line, message), where a diagnostic on a generated block also carries the line of the block it was generated for (`OriginLine`); a diagnostic is rendered as `file(line): ERROR VM042: message`, on a generated block as `file(line, from 12): ...` (D98). A block the expander generates has the line of its origin, so a diagnostic on it reads `file(12, from 12)`, and its message starts with the rule or rewriter that made the block and its reason, `[tool_change] (pre): ...` (D200). ERROR stops the run; WARNING is reported and the run continues; INFO carries notes that are neither (a plugin's inserted blocks) and never changes the outcome or the exit code.

## 3. Block execution

For every block:

1. Parse the words. Unknown key, wrong value type, duplicate key, two verbs, axis words without a verb: ERROR. A key of the form of a machine axis (D93), in a block that carries `CYCLE:<controller>=n` a native parameter (D94), and in a block of a catalog cycle (`CYCLE=RECT_POCKET`) a cycle parameter (D114) are not unknown keys; they are resolved in step 2 (3.8), carried unresolved, or checked against the machine's cycle catalog when the `CYCLE` word is applied (3.3). A key starting with `@` is a pseudo-word (3.10): accepted, with a state key as its value, only in a block the expander generated; in a user file it is the ERROR "pseudo-word in a user file" (D95).
2. Resolve role addresses and axis names against the machine configuration (3.8).
3. Apply the state words, in any order; they do not depend on each other within a block, with one exception: in a block with both `TOOL` and `PRELOAD`, `TOOL` applies first, so the change comes before the preload of the next tool (language 4.4, D132). A `CYCLE:<controller>=n` word sets the cycle and stores the native parameters of the block unresolved, in source order; the VM does not interpret them (D94).
4. If the verb is `SHIFT`, `TILT`, `TILT_AXIS` or `SETPOS`, update the frame. `STOCK` is a verb that moves nothing and updates nothing; its axis words are the corners of the blank, not targets (D351).
5. If the verb is a motion verb, resolve the target (3.1 to 3.3) and execute it. `HOME` moves the named axes at rapid to the reference point of the configuration (`POINT=2` selects the second reference point); afterwards those axes are known in the MACHINE frame at the reference coordinates. `HOME` on an axis without a reference point in the configuration is a WARNING, once per run and axis, and the axis becomes unknown in every frame afterwards; a compiler that must write the coordinates reports the ERROR (D100).
6. Reset block-scoped items: `FRAME`, `IF`, `ARG`, `TIMES`, `WITH`.
7. Raise the block's events (section 7).

### 3.1 Linear motion

Target = current position with the given axis words applied: `X=` replaces, `IX=` adds to the current value (ERROR when the current value is unknown). An axis known only in the other of the workpiece and the MACHINE frame (after `HOME`, D35) takes the increment in the frame it is known in when the two frames differ on this axis by shifts alone (the default workpiece holder, no `ROTATE` in a plane holding it, no `MIRROR` of it, no `TILT` or `TILT_AXIS` in the chain); it stays known in that frame only, and every other case is the ERROR (D183). Axes not mentioned keep their value. `LINE` with feed.value none: ERROR, and so is an `ARC` with feed.value none, which is interpolated at `F` exactly as a `LINE` is; `CYCLE_CALL` stays outside the rule, because its feed is `CYCLE_F` (D29, D184). Motion before `UNITS`: ERROR. Inside a subprogram that no program of the file calls these three rules are suppressed and an incremental word leaves the position unknown instead of raising the ERROR (3.9, D99); at a `CALL` the subprogram runs with the caller's position, so the rules apply there as anywhere else. Under `DIAMETER=ON`, `X`, `IX` and the absolute `CENTER:X` are halved before they reach the position store, whatever the verb: the `X` of a `SETPOS` and of a `SHIFT` as well, so `SHIFT X=20` shifts by radius 10 (D125); `CENTER:IX`, `R` and other radial distances are radius values already (D60). While `POLAR=ON`, the working plane for `ARC` and for `COMP` is the face plane whose axes are the X word (a diameter under `DIAMETER=ON`, D60) and the C word as a Cartesian length in the active units; the position is known in that polar frame and unknown in the workpiece frame; `POLAR=OFF` leaves X and C unknown in the workpiece frame until the next motion with known coordinates (D35); `R` and `CENTER` keep their meaning in that plane. `CYLINDER=n` is treated the same way with the cylinder axis in place of X and the C word as a length on the circumference (D102): the cylinder axis is the linear axis parallel to the rotary axis of the current workpiece holder, Z for an axis owned by a work spindle, otherwise the `[[axis]] parallel` of that axis (default Z), and the C word names that rotary axis whatever its machine letter; the radial tool axis is X about Z and Z about X or Y. The VM does not check that the spindle axis is perpendicular to the table axis, which is the kinematics module's job (D146). The kinematics module resolves the Cartesian workpiece position when present.

Vector form (D81, D185): a `RAPID`, `LINE` or `ARC` under `TCPM=ON` may carry `TX TY TZ` (tool axis direction at the end point) and optionally `NX NY NZ` (surface normal), both unit vectors in the active workpiece frame, instead of rotary axis words. The VM checks the length (1 within the arc tolerance, else ERROR), stores the vectors as written, marks the rotary axis positions unknown and does not resolve the vectors to axes; the kinematics module does that when present. Rotary words and vector words in one block, or vector words without `TCPM=ON`: ERROR. The vector has one meaning under every verb, the tool direction at the end point; vector words in a `CYCLE_CALL` block are the ERROR VM214 (D185).

#### 3.1a Retract

`RETRACT` moves the tool axis only, away from the workpiece: by the given distance, or bare to the machine limit of that axis. Without an active `TILT` or `TILT_AXIS` the tool axis is the axis perpendicular to the `WORKPLANE`, and the VM moves it (to the axis `limits` from the configuration for the bare form, unknown when there are none). Under a tilt the direction is known only with the kinematics module; without it the moved axes become unknown, which is what the unknown rule after machine-frame moves already does (D35). A `RETRACT` with a feed or with other axis words: ERROR.

### 3.2 Arc

`F` is the feed along the arc length in the working plane together with the travel of every linear axis the block moves outside it, so a helix feeds along its three-dimensional path (D353). Only in the working plane, which under `POLAR=ON` or `CYLINDER=n` is the polar or cylinder plane of 3.1 (D102); `WORKPLANE=ZX` and `YZ` use the G18/G19 axis orientation for the direction; in the polar plane the direction is seen looking against the tool axis onto the face with X as the first and C as the second plane axis (the `G12.1` and `TRANSMIT` convention), in the cylinder plane looking onto the developed surface with the cylinder axis first and C second (`G7.1`, `TRACYL`), independent of `WORKPLANE`. Start = current position, must be known in the plane. End = start with the axis words applied. A tool-axis word makes a helix. The MOTION event keeps the resolved centre at the precision of the virtual machine (six decimals, D121); the compiler writes the rounded end point and may move the written centre inside its rounding step where the rounded centre misses `arc_radius_tolerance` (D364).

`CENTER` form: `CENTER:X` absolute or `CENTER:IX` relative to the start point; both plane axes required. The VM validates |start - center| against |end - center| with the tolerance from the machine configuration, `[machine] arc_tolerance` in millimetres converted for an INCH program (default 0.01 mm, 0.0005 in; D139). Start = end is a full circle, compared exactly: the plane coordinates are equal as the position store holds them (the VM precision of D121). An end that lies near the start but not on it is the short arc, or the near-full turn, that its coordinates and the direction of the verb give; the arc tolerance never makes a full circle of it (D122). A center that lies on the start point (radius 0) is an ERROR (D122).

`R` form: signed radius. With d = |end - start|, d > 2|R| plus tolerance is an ERROR. h = sqrt(R² - (d/2)²), M = midpoint, u = (end - start)/d, n = left normal of u. Center = M + s·h·n with s = +1 for (CCW, R > 0) and (CW, R < 0), s = -1 otherwise. Start = end with `R`: ERROR. The VM keeps the computed center, so the compiler can write either form.

`ANGLE` form (D84): `CENTER` required, no plane end-point words, no `R`. The end point in the plane is the start point rotated about the center by `ANGLE` degrees in the direction of the verb; `ANGLE` greater than 360 is more than one turn, and a tool-axis word distributes its travel over the whole sweep (a helix of `ANGLE`/360 turns). The VM stores start, center, sweep and end, so the compiler can write full turns plus a rest for controllers that take at most one turn per block, or the sweep form for controllers that have it (Siemens `TURN=`, Heidenhain `CP IPA`).

Every coordinate the VM computes (the centre of an `R` arc, the end of an `ANGLE` arc, the sweep and every other double of the arc geometry, the length of a motion) is stored at one fixed VM precision that does not depend on the machine: 6 decimals, rounded half away from zero (language 4.12, `ROUND`), in `MM` and `INCH` alike (D121). Trace then reads 69.025871, a computed point that should equal a written one compares equal (6.9999999999997 becomes 7, which the exact start = end comparison of D122 relies on), and the compiler's `[format]` rounding alone decides the written digit.

### 3.3 Cycle call

Requires cycle.name not OFF and, for the built-in family, `DEPTH` and `CLEARANCE` written. The parameters of a catalog cycle are checked when its `CYCLE` block is applied: a name the machine's cycle catalog does not map for that cycle is an ERROR (VM254), and without a machine file the WARNING "not checked: no machine file", once per name (D103, D114). Known means written here: a plane from an expression in STATIC mode is no ERROR, it counts toward the WARNING "unresolved expression" of section 5, and a plane without a value (an expression, or `SAFE` missing under `CYCLE_RETRACT=SAFE`) makes the motions to it and the drilling axis after the call unknown. The ERROR falls to the compiler that must write the plane (Heidenhain `Q204`, Siemens `RTP`); the Fanuc compiler writes `G98` and needs none (D188). The drilling axis is `AXIS` of the cycle, by default the tool axis of the active `WORKPLANE`; the other axis words of the call block position the hole (on a lathe with `AXIS=X` these are `Z` and `C`). A word on the drilling axis itself is an ERROR: the sequence below moves that axis, and a pre-positioning is a `RAPID` of its own (D189). Sequence: rapid in the plane to the axis words at the current drilling-axis position (if any), rapid to `CLEARANCE`, feed to `DEPTH` with `CYCLE_F` (pecking with `PECK`, dwell with `CYCLE_DWELL`, spindle reversal for `TAP`), retract to `CLEARANCE` or `SAFE` per `CYCLE_RETRACT`. Under `DIAMETER=ON` the X values of an `AXIS=X` cycle are halved like every other X. Position afterwards: plane axes at the call point, drilling axis at the retract plane. `CYCLE_CALL` is raised at every call; with the VM option `ExpandCycles` the MOTION events of the sequence follow it in the same block and carry the `CYCLE_CALL` block as their block (used by analytics, D234). They move as follows (D190):

- a rapid in the plane to the call point, then a rapid to `CLEARANCE`;
- a known `PECK` above 0 splits the feed into steps of `PECK` on any cycle of the family, counted from `SURFACE`, or from `CLEARANCE` without one (D355). Between the steps `PECK` returns at rapid to `CLEARANCE` and comes back at rapid to `[cycles] peck_clearance` above the depth reached; `CHIP_BREAK` lifts by `[cycles] chip_break_lift` at rapid and feeds on without leaving the hole. A key the machine file does not set is the family's behaviour (machine-config 6, D357);
- `CYCLE_DWELL` is time at `DEPTH` with no motion (section 8 adds it);
- the retract is a rapid, for `BORE` after the spindle stop. `TAP` and `REAM` feed out at `CYCLE_F`. `TAP` feeds only to `CLEARANCE`, and under `CYCLE_RETRACT=SAFE` the rest of the way to `SAFE` is a rapid. Under `CYCLE_RETRACT=SAFE`, `REAM` feeds up to the plane of `[cycles] ream_feed_out` and rapids the rest; absent, `CLEARANCE` on Fanuc and Heidenhain and `SAFE` on Siemens (D378). Under `CYCLE_RETRACT=CLEARANCE` both feed to `CLEARANCE` and stop.

The CAM's simulation reads the same keys with the same defaults (opencam D-061), so the expanded motions and the CAM's picture agree. A run without a machine family takes 0 for both distances and `CLEARANCE` for `REAM`. The lift and the re-entry never go above `CLEARANCE`. For a `CYCLE:<controller>=n` cycle, and for every cycle of the catalog outside the built-in family, the VM does not know the sequence (D94, D187): the call positions the plane axes at the axis words of the call block, the drilling axis is unknown afterwards, and `ExpandCycles` raises no MOTION events for it; the `CycleCallEvent` carries the native parameters as words. One exception: after the call of a Fanuc turning cycle that the control ends at its start point — `G90`, `G92`, `G94` (`G77`, `G78`, `G79` in the G-code systems B and C) and the one-shot `G70` to `G76`, `G71` and `G72` of type I and II included — no axis has moved and none becomes unknown, because the words of such a call are the end point of one pass and a turning cycle has no drilling axis (D187, D411). The turning cycles of the other families keep the rule above until their end positions are confirmed.

### 3.4 Position frames

Initial position: an axis whose `[[axis]]` entry has `home` starts known in the MACHINE frame at that reference point and unknown in the workpiece frame (D35, D100); an axis without `home` starts unknown in every frame. A motion that names some axes leaves the others as they were. A `FRAME=MACHINE` block moves in machine coordinates; afterwards the moved axes are known in the MACHINE frame and unknown in the workpiece frame unless the configuration provides the datum table. A `SHIFT` appended to the chain is folded into the position: newPos = oldPos - shift, expressed in the frame active where the word stands; a `RESET` that removes shifts folds them back. The four frame verbs take absolute axis words only, each the kinds language 4.2 gives it, so nothing is ever folded from an increment under them (D117). `SETPOS` moves nothing: for every axis word it records a setpos shift such that the current position reads as the declared value (newSetposShift = oldPos - declared); the position store keeps its physical value, the workpiece coordinates are read through the setpos shift, and the next `ORIGIN` clears it (as `G54` cancels a `G50`/`G92` setting). The setpos shift keeps its displacement in space: when a `RESET` removes a `ROTATE` or `MIRROR` with a known value that stood before the `SETPOS`, the VM turns the shift into the frame that remains (R·s, a mirrored axis negated); a removed `SHIFT` only folds back; after a removed `TILT`, `TILT_AXIS` or an angle from an expression the shift becomes unknown (D319). `SETPOS` needs the axis known in some frame: when it is known in the MACHINE frame only (after `HOME` or a machine-frame move), the setpos shift is recorded against the machine position and the axis becomes known in the workpiece frame with the declared value; directly after a `HOME` of that axis that found no reference point in the configuration (D100), `SETPOS` is accepted as well: the axis becomes known in the workpiece frame with the declared value and its machine position stays unknown; that permission lasts until the next block that names the axis (a motion, a `HOME` or a `SETPOS` with it) or that switches the spindle owning the axis to `SPINDLE` mode, so blocks that touch neither may stand between the `HOME` and the `SETPOS` (D127); the ERROR remains for every other axis unknown in every frame (D101). `POLAR=ON` puts X and C into the polar frame of 3.1, `CYLINDER=n` puts the cylinder axis (the linear axis parallel to the rotary axis of the workpiece holder: Z for a work spindle, the `[[axis]] parallel` of a table axis otherwise, D146) and C, which names that rotary axis, into the cylinder frame of 3.1, X staying a workpiece coordinate: from the first motion under the transformation their positions are known in that frame and unknown in the workpiece frame; `POLAR=OFF` and `CYLINDER=OFF` leave them unknown in the workpiece frame until the next motion with known coordinates, like a machine-frame move (D35, D102). `TILT`, `TILT_AXIS`, `ROTATE` and `MIRROR` changes mark the position unknown in the new frame unless the kinematics module is present to convert. `ORIGIN=n` selecting a datum other than the active one is such a frame change as well: every axis known in the workpiece, polar or cylinder frame becomes unknown, since no datum table relates two datums (D35); MACHINE-frame knowledge and the setpos handling stay. `ORIGIN=n` repeating the active datum empties the chain as a `RESET` does and keeps the rest (D123). A `TILT` or `TILT_AXIS` turns the linear frame only: a rotary axis word under it moves the machine axis by its workpiece-coordinate difference, as under `ROTATE`, so its recorded machine position stays known, and it couples no linear axis (D230). `MOVE=TURN` or `MOVE=MOVE` on a tilt additionally marks the rotary axes as moved to the plane (their positions are known only from `TILT_AXIS` words, as machine-axis setpoints in the MACHINE frame, where the limit check applies (D100); their workpiece-frame value stays unknown until a motion with known coordinates, so an `IC` right after is the ERROR of 3.1 (D126, D230); unknown after a spatial `TILT` without the kinematics module); `MOVE=STAY` leaves them. `WORKPIECE` changes mark the position unknown in the new holder's frame until the next motion with known coordinates (D123). The frame of a holder is its own right-handed frame with +Z out of its chuck (D57): the VM stores sub spindle positions in that frame, and readers and compilers apply the machine's mirror or datum convention outside the VM.

### 3.5 Tool change

The two-word model (`PRELOAD`, `TOOL`) is executed against the holder state:

| Word | Effect on holder state | Diagnostics |
|---|---|---|
| `PRELOAD=n` | preloaded = n (0 clears) | WARNING when n is already in the spindle (no-op on the machine) |
| `TOOL=n` | spindleTool = n; preloaded = none (TOOL=n consumes any preload, D132); raises TOOL_END for the old tool and TOOL_BEGIN for n | WARNING when a different tool was preloaded (the magazine has to cycle twice) |
| `TOOL` | spindleTool = preloaded; preloaded = none | ERROR when nothing is preloaded |
| `TOOL=0` | spindleTool = 0 | WARNING when a cycle is still active or compensation is on |
| every form of `TOOL` | toolPoint = 1, tipOffset = 0, pointRadius = 0, then the point words of the block (D372) | |

Readers produce these words from the source (see `controller-mapping.md`): Fanuc `T4 M6` gives `TOOL=4` in one block; `T5` alone gives `PRELOAD=5`; `M6` alone gives `TOOL=n` from the source-side VM. The compiler decides the output form from the machine's `[tool_change]` settings: `T4 M6`, `M6` alone when preloaded, `TOOL CALL 4 Z S1592` (folding the `WORKPLANE` and the `RPM` of the same or the following block into the call, the following block being the first one after the `TOOL` block, in its section, that holds more than `PRELOAD` words, D275), or `T0404` on a turret. When `auto_preload = true` and the program contains no `PRELOAD` words, the compiler inserts a preload of the next tool after each change using the STATIC pre-pass; a program that has its own `PRELOAD` words is left alone. The `PRELOAD` words of the subprograms a program calls count as its own (D267 (b)). A change command with `{next}` at the last change of a program prepares the program's first tool, with the WARNING CMP006 where that is the tool being changed in (D267 (a), machine-config 3).

### 3.6 Expressions and control flow (INTERPRETED)

- Pre-pass over the file collects the `PROGRAM` sections, the `SUB` sections by `NAME` and the `LABEL`s of every section; duplicates, missing targets, a `LABEL=END`, a `SUB` inside a `PROGRAM` or a block outside every section are ERRORs before execution. The program that runs is the first of the file unless the job manifest or the command line names another.
- Variables start from `<file>.vars.toml` when present. Reading an unassigned variable is an ERROR unless the configuration sets `unassigned = 0`. A `SYS_` name, indexed or not, reads its value from the vars file wherever the VM has none, also when the configuration does not map the name (`"SYS_WEAR_Z[99]" = 0.012`, machine-config 8); without one there it is an ERROR in INTERPRETED mode whose message names the vars file, as 2.7 says (D120).
- `IF` evaluates to 0 or not 0. `IF` without `JUMP` or `CALL`: ERROR.
- `JUMP` sets pc to a `LABEL` of the current section, forward or backward (a `LABEL` directly after the header makes the program loop, which is how readers render a Fanuc `M99` in the main program); `JUMP=END` sets it to the `PROGRAM=END` of the current program, also from inside a subprogram (WARNING: it ends the program from a call, as a Fanuc `M30` in a subprogram does; the Siemens compiler writes it as the parameterized return `RET("<end label>",,$P_STACK)`, since an `M30` in a SINUMERIK subprogram only returns to the caller, D344). `CALL` pushes return pc and the local variables `V1`..`V33`, assigns `ARG` words to the callee's locals (every name an `ARG` assigns is a local of that call, hiding a caller variable of that name until `SUB=END` or `RETURN`, D149), and enters the `SUB` section of the file or loads the external program (searched in the working directory). The callee's `V1`..`V33` start unassigned apart from the `ARG` values, as the locals of a Fanuc G65 macro call do: the call raises the local-variable level, a local that received no argument starts vacant, and the return restores the caller's (D148). `SUB=END` and `RETURN` pop. `RETURN` in a program with an empty stack: WARNING, treated as `JUMP=END`.
- `PROGRAM=END` ends execution of the program: the channel is finished, the run statistics are raised. A `CALL` that names a program instead of a subprogram: ERROR; that ERROR names a program of the caller's own file, not a program that `CALL="name"` runs from another file (D214).
- A `CALL="name"` enters the first program of the external file. Its `PROGRAM=BEGIN` block, with `NAME`, `NUMBER` and `CHANNEL`, is its frame and is not executed; its `PROGRAM=END` returns to the caller as a `SUB=END` does, and so does a `RETURN` in it, and a `JUMP=END` in it goes to its own `PROGRAM=END` and so also returns. No program-end effect applies: the channel does not end, the resets of section 4 do not run, the caller's program name stays, and neither `PROGRAM_BEGIN` nor `PROGRAM_END` is raised for it. The `CALL` event marks the call, and the blocks it ran count towards the statistics of the caller's `PROGRAM_END` (section 7, D214). This is how a called program ends on the controls: a Fanuc `O` program ends with `M99`, a Siemens one with `M17` or `RET`, and the SINUMERIK treats the `M2` or `M30` of a main program called as a subprogram as `M17`; the TNC runs a called program to its program end and continues the caller with the block after the call.
- `SKIP` blocks are executed unless the run option `skip_blocks` (or `skip_blocks = [0, 3]` for the switches that are on) says otherwise. A bare `SKIP` is the first switch and has the number 0 in the list, so `skip_blocks = [0, 3]` skips the bare `SKIP` blocks and `SKIP=3`, a list without 0 leaves the bare ones running, and `all` skips every `SKIP` block; the program word `SKIP=n` still names 1 to 9 (language 4.1, D133). A `LABEL` on a skipped block still counts as a target.
- `$SYS_*` variables are read from the VM state through the configuration's mapping (position, active tool, offsets). A `$SYS_*` name the configuration does not map, or a state that is unknown, evaluates to UNKNOWN in STATIC mode and is an ERROR in INTERPRETED mode.
- `REPEAT` re-executes the section from the label to the current block `TIMES` times, once without `TIMES` (D212); nested repeats and calls up to the configured depth (default 8). A `JUMP` or `JUMP=END` to a target outside the label..`REPEAT` section ends the repeat, and a later arrival at the `REPEAT` starts it fresh with `TIMES` passes; the compilers reproduce this (D213).
- Block cap from the configuration (default 1 000 000): ERROR "possible endless loop".
- `CALL="name"` loads `<name>.ncx` from the working directory and no other file: the name is the program's file name without folder and extension, and a missing target is the ERROR that names the file it looked for (D215).
- An external program must have its own `PROGRAM` frame and must not contradict the caller's `UNITS` and `WORKPLANE`: ERROR. A source file of subprograms only therefore reads as a program as well (D210). The file still checks on its own (section 1), where its `PROGRAM=END` ends its channel as any other program's does.

### 3.7 Channels and the job scheduler

A job runs one VM per channel program and advances them in rounds: every channel that is neither finished nor waiting executes one block. `SYNC=m` marks the channel waiting at m; when all participants (`WITH`, default all) wait at m, all are released. Marks are matched in execution order, not by uniqueness: a program may wait at the same mark many times (the DMG templates do), and two channels waiting at different marks with the same participants is the deadlock case below. The channels waiting at one mark name the same participants: a channel that reaches mark m while another participant of either list waits there with a different set is the ERROR VM573 ("channels at mark m name different participants: ch1 WITH=1,2; ch2 WITH=1,2,3"), and the job stops there instead of running into the deadlock; NCX does not model the Siemens per-channel release, since the control itself calls the behaviour after it undeterminable, and on Fanuc the P lists would raise alarm PS0160 (D304). `WAIT_CHANNEL=c` waits for channel c to finish; a `WAIT_CHANNEL` on a finished channel is released. When no channel can execute a block and some channel has not finished, whether the others wait or have finished, that is the deadlock ERROR VM571, which names what each channel waits for (D305). A channel named by a `START_CHANNEL` anywhere in the job's files waits to be started; every other channel starts in the first round; the started channel runs the program its `NAME` selects, else its `[[channel]]` program. A `START_CHANNEL` of a running channel is the WARNING VM852 and starts nothing (the control requires Reset or interrupted). A `START_CHANNEL` of a finished channel starts nothing either, with the WARNING VM856: the control would restart it, but NCX runs one program per channel per job. This is an NCX restriction, not a Siemens rule (D309). A `WITH`, `WAIT_CHANNEL` or `START_CHANNEL` that names a channel not in `[machine] channels` is the ERROR VM851 (the control alarms too, Fanuc PS0161). One that names a channel the machine has but the job does not run is the WARNING VM855, and the word is taken as if that channel were not named: `WITH` without it, `WAIT_CHANNEL` does not wait, `START_CHANNEL` starts nothing. The compiler writes the word unchanged, with the channel, because the program is for the whole machine (D306). The manifest decides the channel: a header `CHANNEL` that differs from it is the ERROR VM853, because the reader resolved T words and channel-bound functions for the header's channel; a header without `CHANNEL` runs silently on the manifest's channel (D307). `SYNC` in a single-channel job: WARNING, no wait. Without a manifest, a run is a single-channel job when the machine has one channel (`[machine] channels` names one, or the key is absent) and all programs of the file run on one channel; a file for one path of a multi-channel machine gets no `SYNC` WARNING, and `check --job` checks its marks (D196). Resources are per job (2.8, D308): the spindle and holder state is read and changed by every channel's VM in round order, and the Before of a channel's next block takes them as they stand, so a listener sees only the changes of its own channel's blocks. The UNKNOWN marks of the spindle rows are shared with them, so a speed one channel sets from an expression is UNKNOWN in every channel. In a job a channel takes a spindle for its feed per revolution (the default spindle fallback of D288) and for the `WORKPIECE` change WARNING only while that spindle is its own: one whose `[[resource]]` names the channel or that turns because of the channel's own `SPINDLE` word; otherwise the workpiece spindle. The `PROGRAM=END` of a channel resets the spindles the channel owns (a spindle whose `[[resource]]` names the channel, or the tool spindle of a holder that does) and a spindle no channel owns once every channel of the job has ended, since another channel may still turn it (4). Two channels commanding a spindle or axis of `[shared]` between two marks is a WARNING (machine-config 8, D20).

### 3.8 Resource and axis resolution

1. A role address resolves through `[roles]` to a resource id; unknown role or wrong resource type: ERROR; when no machine file is given the default machine of D103 applies and an unknown role is the WARNING "not checked: no machine file" (below).
2. No role address: `SPINDLE`, `RPM`, `VC`, `CSS`, `RPM_MAX`, `ORIENT` target `default_spindle`; `TOOL`, `PRELOAD` target `default_holder`; `OFFSET`, `OFFSET:*` the holder of the last `TOOL`. A reader therefore writes the holder's role on a `TOOL` of a holder other than `default_holder` — the holder whose `channel` is the channel of the program (D219). More than one resource of a kind without an explicit default in the configuration: ERROR when the machine is loaded.
2a. Every function the compiler writes for a resource comes from that resource's template table in the configuration (`[spindle.MAIN] CW = "M3"`, `[spindle.SUB] CW = "M53"`, Doosan `CW = "M3 P11"` (the file may write `"M03 P11"`; the loader normalizes every M or G code and the compiler writes the normalized form, D105), DMG `[spindle_mode.MAIN] AXIS = "L707({angle})"`); the VM only knows the abstract word. A template table may be bound to a channel (`channel = 2`: the machine accepts the code only from that path, as Nakamura does for the spindle synchronization codes) or to all channels (`channels = "all"`: the code must stand in every path's program behind a wait, as Mori Seiki requires for `M34`/`M35`); `state_channels` binds single states apart from their table, the Mori Seiki `M36` to channel 1 alone (D414). The VM ignores this; the job compiler moves or duplicates the words and adds the `SYNC` it needs, and a single-channel compile reports an ERROR for a word bound to another channel (D56). A moved word stands directly after the `SYNC` of the same release in the owning channel's program, as an NCX rule, after the `PROGRAM=BEGIN` when no mark stands before it; a channel without that mark is the ERROR CMP704 (D313). A bound word that must be moved or duplicated may not stand in a `SUB`, and neither may the mark it would follow: the ERROR CMP703 (D311). A rule's generated blocks stay in the program that writes the word; only the bound word moves or is duplicated, it is not expanded again, and bound words among the generated blocks move by the same rule (D328). The generated `SYNC` takes the first mark of the range of all the job's channels that no channel program uses and that is neither `start_mark` nor among `reserved_marks` (D315). A word bound to every channel that every channel program of the job already writes, with the same canonical text, between the same two marks stands behind that wait already and is not duplicated; where two channels write such words between the same two marks (or both before every mark) it is an ERROR, because the generated `SYNC`s pair in execution order and the order is one the author states with a `SYNC` of their own (D312).
3. Of `A`, `B` and `C`, the one whose letter the current workpiece holder's rotary axis carries — the axis's NCX name without its digits, so `C2` gives `C` — resolves to that axis; every other one resolves to the machine axis with that NCX name, so a swivel `B` and a linear `A` or `B` slide keep their own axes (D147). Explicit machine axis names resolve through the `[[axis]]` list; anything else is an ERROR (D93). When no machine file is given the default machine of D103 applies and an axis it does not have is a WARNING.
4. `SPINDLE_MODE:r=AXIS` (the role address is required, D113): `SPINDLE:r` is an ERROR until back in `SPINDLE` mode; `C=` on that axis is allowed. In `SPINDLE` mode, every word that positions that axis or declares its position is an ERROR: `C` or `IC` under `RAPID`, `LINE`, `ARC`, `CYCLE_CALL` or `SETPOS`, the bare `C` of `HOME`, and the `C` of a `TILT_AXIS` with `MOVE=TURN` or `MOVE=MOVE`. A `SHIFT C=` is a chain entry and moves nothing, and a `TILT_AXIS` with `MOVE=STAY` leaves the axis standing; neither is covered (D131).
5. `SPINDLE_SYNC=a,b` needs two work spindles in `SPINDLE` mode; `RPM:b` and `SPINDLE:b` while synchronized are WARNINGs. `PHASE` without `SPINDLE_SYNC` in the block is an ERROR.

Without a machine file, `check`, `trace`, `annotate` and `analyze` run against a built-in default machine of one channel (D196): one work spindle `MAIN` with the C axis, one tool holder `TOOL` with the tool spindle `TOOL`, axes `X Y Z A B C` without limits and without reference points, coolant channel `STANDARD`, no named functions, the arc tolerance of D36, units default `MM`, and `default_spindle` the tool spindle `TOOL`, so bare spindle words drive the tool of a mill program (D129). A role, function, coolant channel or machine axis the default machine lacks, and a parameter of a catalog cycle (the default machine has no cycle catalog, D114), is a WARNING "not checked: no machine file", once per name, and the word runs against a resource created on the spot: every spindle word and `WORKPIECE` create a work spindle, `TOOL` and `PRELOAD` a holder without a spindle. A created resource's id is `ROLE_<role>`, never equal to an id of the default machine such as `S2`, and a work spindle created this way gets the rotary axis `C_<role>` of its own, so `C` resolves to it while it is the workpiece holder (rule 3, D170). With a machine file the rules above apply in full; `convert` and `compile` keep requiring a machine file (D77, D103).

### 3.9 Subprograms and the other programs of the file

A file holds programs and subprograms side by side (language 4.13). In INTERPRETED mode a subprogram is executed only when a `CALL` enters it, with the caller's state, exactly as on the control; the other programs of the file are not executed unless the job runs them on their channels. In STATIC mode a subprogram is walked at every `CALL` with the caller's state at that point, so that `check` validates it as the caller enters it; a subprogram that no program of the file calls is walked once from the default entry state of section 1, and inside it these validations are suppressed because the state they depend on belongs to a caller that does not exist: `LINE` or `ARC` without feed (D184), motion before `UNITS`, tool and offset rules, cycle rules, an incremental word from an unknown position (the position becomes unknown, no ERROR), spindle OFF before a `LINE`, an `ARC` or a drilling `CYCLE_CALL` (D194). Everything structural stays (unknown words, axis words without verb, a missing `SUB=END`), and the compiler emits each `SUB` section once, not once per `CALL`; where the target needs the section per program (Heidenhain, language 4.13) it is once per calling program (D99), and a section no program calls is written once all the same, after the last program or into the first program's file (D264), and in a job compile into the library file of the job (D316). It writes the section from an unknown target state, so that every modal word stands at its first use inside it and the text is right for every caller; walks of the section that would write different lines are an ERROR naming the section and the calls (D99). The STATIC walk keeps a call stack like INTERPRETED mode and applies the configured call depth (3.6, default 8): a `CALL` beyond it is the ERROR "call depth exceeded" and the subprogram is not entered again. A `CALL` with `TIMES=n` is walked n times in sequence in STATIC mode, each time from the state the previous pass left, so the caller continues with the state after the last pass; a `TIMES` from an expression is walked once, the axes that pass moved become unknown, and the expression counts toward the WARNING "unresolved expression in STATIC mode" (D136). A `CALL` of an external program is not followed in STATIC mode (section 1): the call is recorded and the position becomes unknown. Inside a program or subprogram, a block after an unconditional `JUMP` that no `LABEL` makes reachable is unreachable: WARNING. `JUMP`, `RETURN` and `JUMP=END` are unconditional exits, and `SUB=END` is never unreachable (D195). This is where the jump-entered sections of a source end up that the control kept below its `M30` (the reader moves them in front of `PROGRAM=END` behind a `JUMP=END`).

A contour section that a Fanuc `G70`..`G73` names with `CONTOUR=` is walked like a subprogram no program calls, from the default entry state, and the Fanuc compiler writes the blocks of that walk inline after the cycle that names it instead of as an `O` program, with the motion code and the feed unknown at its first block, the plane, the feed mode and `G90`/`G91` of the walk written in front of the cycle line, and the cycle, the compensation and the units pinned to the walk's own values, so that the range holds `G00`..`G03`, `G04`, axis words and `F` only; after every cycle that runs the range, the codes and the feed of its blocks are unknown. A section that a `CALL` also enters is written as a subprogram as well (D278, D388 item 4).

### 3.10 Generated blocks

A generated block carries its origin (the block it was generated for, the rule or plugin that made it) and two internal pseudo-words that only the expander may write, `@SAVE=SPINDLE:MAIN` and `@RESTORE=SPINDLE:MAIN`, whose value is a state key of the form `KEY[:ADDR]` naming a state variable of the channel by the key that sets it (`SPINDLE:MAIN`, `COOLANT`, `F`); the lexer accepts a key starting with `@` only under the parser option the expander uses for generated text (D95). `@SAVE` pushes the current value of that variable on a restore stack; `@RESTORE` pops it and re-applies it as if the program had written the word again (a saved `SPINDLE:MAIN=CW RPM:MAIN=1500` comes back as those two words, so the compiler writes `M3 S1500`). This is how a rule that had to stop the spindle gets it running again without knowing the speed. The restore stack keeps `SPINDLE`, `RPM`, `SPINDLE_MODE`, `CSS`, `VC`, `RPM_MAX` (per spindle), `COOLANT` (per channel), `FUNC` (per function), `F`, `FEED_MODE`, `COMP`, `DIAMETER`, `WORKPLANE`, `TCPM`, `POLAR`, `CYLINDER`, `ROTARY_PATH`, `ROTARY_FEED` and `TOLERANCE`, which comes back with `TOLERANCE:ROTARY` and `TOLERANCE_MODE`. Any other key is the ERROR VM681: `TOOL`, `PRELOAD`, `OFFSET`, `CYCLE`, `ORIGIN`, `SETPOS`, the chain words, `SPINDLE_SYNC`, `PHASE`, `ORIENT`, `WORKPIECE`, `UNITS`, variables and positions. `ORIGIN` and `UNITS` stay out on purpose: `ORIGIN=n` written again empties the chain, so it would not bring back the frames that a Siemens `SAVE` restores, and the machine would move in a different frame without a word of warning; a restored `UNITS` would change the unit of values already on the stack. The controls restore a wider set on a subprogram return (Siemens `PROC ... SAVE`, the Fanuc interrupt `M99`); NCX restores a narrower one on purpose (D202). Generated blocks are executed in both modes, count for analytics (a spindle stop and restart costs cycle time and is reported as such), appear in `trace` and `annotate` with their origin, and are never written by `ncx format`. Pseudo-words in a user file are an ERROR (D95). A generated block carries the `SKIP` of its origin unless its own text writes one, so `skip_blocks` skips or runs the group together (D201). In `trace` its block column reads `<line> generated by …` or `rewritten by …`; in `annotate` it is a comment line (D237). A pseudo-word stands in a block of its own; a plugin rewriter whose block mixes one with other words is an ERROR on the plugin, PLG006 (D167).

## 4. Modal summary

The resets of `PROGRAM=END` below belong to the `PROGRAM=END` that ends a program of the running channel; the `PROGRAM=END` of a program that a `CALL` runs from another file returns to the caller and resets nothing (3.6, D214).

| Item | Modal | Reset by |
|---|---|---|
| units, workplane, origin, transform chain, diameter | yes | explicit word only; `ORIGIN` empties the chain |
| setpos shift | yes | `SETPOS` on the same axis, `ORIGIN` |
| verb, `FRAME`, `IF`, `ARG`, `TIMES`, `WITH` | block | end of block |
| feed value and mode, compensation | yes | explicit word; `PROGRAM=END` |
| tool in spindle, preloaded tool, offsets | yes | explicit word; preload consumed by `TOOL`; `PROGRAM=END` keeps the tool in the spindle |
| measurement point, tip offset, register radius (per holder) | yes | explicit word; every `TOOL` on the holder resets them to point 1, 0, 0 (D372) |
| spindle direction, rpm, vc, mode, sync and phase, css | yes | explicit word; `PROGRAM=END` sets OFF, mode SPINDLE, sync OFF; in a job only the spindles the channel owns, and a spindle no channel owns once every channel has ended (3.7, D308) |
| cylinder, polar, tcpm, rotary path and feed, path mode, tolerance, round limit | yes | explicit word; `PROGRAM=END` sets OFF and the defaults, the path mode its start value from `[dynamics] path_mode` (D349, D350, D363) |
| `SKIP`, `PHASE`, `POINT` | block | end of block |
| coolant, named functions | yes | explicit word; `PROGRAM=END` sets coolant OFF |
| cycle | yes | `CYCLE=OFF`, next `CYCLE`, `TOOL` (WARNING), `PROGRAM=END`; these are also where the `post` and `@RESTORE` of a catalog cycle's expansion rule stand (D204) |
| variables | program lifetime; `V1`..`V33` per call, unassigned at entry apart from the `ARG` values (D148) | `SUB=END` and `RETURN` restore locals |
| workpiece holder | yes | explicit word; kept at `PROGRAM=END` |

## 5. Validation

ERROR (run stops): missing or misplaced `FILE=BEGIN`, `NCX`, `FILE=END`, `PROGRAM=BEGIN`, `PROGRAM=END`, `SUB=BEGIN`, `SUB=END`; a block outside every section, a `SUB` inside a `PROGRAM`, a file without a program; `LABEL=END`; `CALL` of a program of the caller's own file (D214); unknown key (a machine axis word, D93, and a native parameter of a `CYCLE:<controller>=n` block, D94, are not unknown keys) or value; unknown role, function, coolant channel (D130, D416) or machine axis word not declared in `[[axis]]` when a machine file is given (3.8 rule 3, D93; without one, the D103 WARNING); a pseudo-word (`@SAVE`, `@RESTORE`) in a user file (D95); duplicate key; two verbs; axis word without verb; motion before `UNITS`; `LINE` or `ARC` without feed (D184); `ARC` without `CENTER`, `R` or `ANGLE`, inconsistent center, a center on the start point (radius 0, D122), radius too small, full circle with `R`, `CENTER` with `R` (D186), `ANGLE` with `R` or with plane end-point words or not greater than 0; vector words without `TCPM=ON`, mixed with rotary words, incomplete or not of unit length, or in a `CYCLE_CALL` block (VM214, D185); `CYLINDER=n` without a rotary axis on the workpiece holder (VM215, D146); ## 6. Trace and annotate

The VM never stores history in the program. Two derived outputs give it instead: `ncx trace` writes one row per changed state variable per executed block (`channel, block, variable, old, new`, old empty when unknown), the measurement point of a holder as `TOOL_POINT:H1`, `TIP_OFFSET:H1`, `POINT_RADIUS:H1` and, where a tip offset stands, the derived tip on the tool axis as `TIP:Z` at the motions, from the `TIP_OFFSET` in effect (2.3; a new value shows from the next tool-axis motion on, not at its own block) (D372, D374); `ncx annotate` writes a copy of the program through the canonical writer with the previous values appended to each block's trailing comment (`LINE X=55.44` becomes `LINE X=55.44` followed by the comment `; X 33.22 -> 55.44` in the canonical column, D92; an existing comment is kept and the values follow it after one space), which the parser keeps as the block's comment and the VM ignores. Several variables of one block are joined by `, `; `annotate` writes an unknown value as `?`, `trace` leaves the field empty (D237). A block of a subprogram that STATIC mode walks at several calls (D99) appears in `trace` once per walk; `annotate` writes the values of its first walk. Both are regenerated at will and read by nothing. When an ERROR stops the run, `trace` writes the rows of the blocks executed before it and `annotate` the whole copy, the blocks not executed without values; each exits 1, and neither writes anything when the run does not start, for a parser or expander ERROR among others (architecture 10, D205).

STATE_CHANGE covers the frame rows of 2.1, feed, feed mode, compensation, the position per axis, the tool vector and the surface normal of 2.2, tool, preload and offsets per holder, the spindle rows per spindle, the coolant channels and functions, and the cycle. Variables go to VAR_CHANGE; the program, flow and channel rows and `lastHolder` are out. The names are the state keys of 3.10 with the resource id as address, positions by axis (D197).

The figures of `TOOL_END` and `PROGRAM_END` are the same: blocks (executed), feedDistance, rapidDistance and unknownLengthMotions, the count of MOTIONs whose length is unknown, so that a report can call the distances a lower bound; distance is their derived total. The distances are sums of the known MOTION lengths, the MOTIONs of an expanded `CYCLE_CALL` and of generated blocks (3.10) included; `RAPID`, `HOME` and `RETRACT` motions go to rapidDistance, as they are rapid motions on the controls and the tool list counts them, and `LINE` and `ARC`, the plunges of an expanded cycle among them, to feedDistance. The figures are exact in INTERPRETED mode; in STATIC mode they count what the walk executes. There is no time figure, which belongs to the runtime estimate of section 8 (D235). A block and its motion count under the tool of `lastHolder`, and a tool-changing block counts under the new tool, so no motion counts under two tools (D236). At the `PROGRAM=END` that ends a channel's program, `TOOL_END` closes every tool the channel brought into a spindle that is still there; the spindle state stays unchanged. The `PROGRAM=END` of an external program run by `CALL` closes nothing, nor does a run stopped by an ERROR (D233).

Each row is one event record of `Ncx.Core` (architecture 5.3). Every event carries `Before` and `After`, the resolved state of the channel around the block. Plugins (the DLL hooks such as `tool_begin`) subscribe here. A plugin has four places to act, and none of them is the VM state (D61): as a reader rule it sees the source blocks and the source-side state of a reader and decides what an M code or a sequence of source blocks means on this particular machine, for example that `M5`, `M51`, `M3 S1500` is one `COOLANT:THROUGH=ON`, or that a builder M code with a hidden subprogram is the workpiece transfer (D66, D231: every source block goes to the plugins' reader rules first, in load order, and a block no rule claims is read by the configuration tables and the family's words; a rule may claim a run of blocks, D232); as a program rewriter in the expander it may change words and insert generated blocks before the VM executes them (clamp a speed, stop the spindle before a function, add a `HOME` before a tool change); as a listener it reads every event; on `BLOCK_WRITE` it edits the output lines of the compiler. Machine limits that are the same for every program (`rpm_max`, `max_feed`, travel limits) do not need a plugin: they are configuration and the expander applies them.

## 8. Analytics

All output is plain text (CSV or aligned columns). Every text table, the `trace` table of section 6 among them, starts with a header row of the column names; aligned text is the default and `--format csv` the other form; CSV follows RFC 4180 with LF line ends (D237).

- Tool list: from TOOL_BEGIN/TOOL_END, with rpm, feeds, offsets, the measurement points in effect during the tool's motions with their `TIP_OFFSET` and `POINT_RADIUS` (`?` for an UNKNOWN value; point 1 with both 0 is not printed, D374), distance, block count, preload behaviour (was the next tool preloaded before the change). The rpm of a tool is the range of its cutting motions; under `CSS` a motion that changes X contributes the two extremes, the rpm at its start and the rpm at its end X radius, each capped by `RPM_MAX`, not the mean the runtime estimate times it with (D289), so a facing cut to the centre spans the low rpm it begins at and the capped rpm it ends at.
- Runtime estimate: per motion a trapezoidal velocity profile from the machine configuration (D64): the commanded feed (per minute, or per revolution times rpm; under `CSS` the rpm follows from `VC` and the current X radius, capped by `RPM_MAX`; along a cutting motion that changes X the radius taken is the mean of the start and the end X radius, which for a motion at constant `VC` below the cap is the exact integral, where the start radius alone would nearly double a facing cut to the centre, and a `RAPID` takes the end radius, not the mean, because nothing is cut on the way, D289, as do `HOME` and `RETRACT`, which move at the rapid rate as well, D412). The rpm, and the spindle `CSS` follows, is that of the current tool holder's spindle (the default spindle for a holder without one) while that spindle turns; while it stands it is that of the workpiece holder's spindle if that spindle turns in `SPINDLE` mode, the spindle a turning tool cuts on, and otherwise 0, so the motion is not timed (D288). The commanded feed is limited by the `max_feed` of every axis that moves, the block accelerates and decelerates with the smallest `acceleration` of the moving axes, and a block can never be shorter than the control's `block_time`, which is what makes thousands of short segments in 3D and 5-axis programs slow. The path-control state of 2.1, whose start value is `[dynamics] path_mode`, rules each corner, read from the motion before it: `EXACT_STOP` brakes to zero in every block, `CONTINUOUS` carries the speed through corners up to the configured `corner_speed`; where the program changes the mode, the report counts the corners timed in each, and where the machine has no template for the mode asked for, it says the machine cannot express that mode at those corners (D350). Under `CONTINUOUS` the path rests at `DWELL`, a spindle start or stop, `TOOL_BEGIN`/`TOOL_END`, `STOP`, program and file events, a motion not timed, a direction reversal, `CYCLE_DWELL`, a cycle call not timed, every `SYNC`, and every block without path motion that the control executes (`COOLANT`, `FUNC`, `MFUNC`, `PATH_MODE`, `TOLERANCE` and the other machine-function and state blocks); comments, variable computations, `LABEL`, `JUMP` and `CALL` blocks are transparent corners. The end of a `RAPID` is a rest point on a Fanuc-family machine (G00 in-position check) and a corner otherwise, unless `[dynamics] rapid_exact_stop` says otherwise; the report names these rules (D286). The end of a `HOME` or a `RETRACT`, which move at the rapid rate (D287), rests like that of a `RAPID`. A rotary axis limits a motion only in the polar or cylinder plane, its deg/min and deg/s^2 converted to the length of the plane (machine-config 4, D290): under `CYLINDER=r` at r, its `rapid` included, so that a `RAPID` of C alone has a rate; under `POLAR` C turns at v p / r^2 for a path speed v, p being the distance of the line of the block from the centre and r that of the point, so a `LINE` is limited to v <= `max_feed` x r_min^2 / p (in radians), r_min its nearest distance from the centre, and a radial line (p = 0) not at all by C; an `ARC` converts at L, its closest approach to the centre (gap closed 2026-10-28, delegated: D290's nearer-end rule refined to the exact bound v <= Cmax r^2 / p). Only a motion that moves X or C of the face plane is limited there; a block through the centre and a motion of C at an unknown or zero cylinder radius are not clamped by C, each counted on its own line of the report. `RAPID`, `HOME` and `RETRACT` use the `rapid` rate with the same profile (D287); the motions of an expanded cycle are timed as motions, with the distances of `[cycles]` (3.3, D190, D357, D378), and `CYCLE_DWELL` adds its time once per call, at `DEPTH`; a spindle start or stop adds `accel_time` of that spindle, and where `rpm_max` and both speeds are known the linear ramp to it, an NCX estimate: `accel_time` x rpm / `rpm_max` for a start or a stop, x |rpm_new - rpm_old| / `rpm_max` for a speed change while turning and x (rpm_old + rpm_new) / `rpm_max` for a reversal; without `rpm_max` or with a speed unknown (`CSS`, no `S` yet) the whole `accel_time` per start and per stop, a reversal twice, nothing for a speed change (D323); a `[cycles]` key the expanded cycles needed and the machine file leaves out, where the family's behaviour is 0, is named by a report line (D357); totals per tool, per section, per channel; job time as the longest channel including waits at marks. Without dynamics in the configuration the estimate falls back to distance over feed and says so.
- Travel limits: min and max per axis in the MACHINE frame against the `limits` of `[[axis]]`, which are machine coordinates (D100); a rotary axis with `modulo = true` is left out, its limits being the display range (D193); a position known only in the workpiece frame is not checked and the report says so; blocks that exceed them.
- Datum, feed and speed lists: from STATE_CHANGE.
- Segment length and tool vector change: for every MOTION, the euclidean length (the arc length with the travel of a helix for arcs, D353) and the angle between the tool vectors before and after (rotary axes A, B, C applied to the tool axis). Specialist checks for CAM output quality.
- Every analytic accepts a block range (`--from 380 --to 600`, NCX line numbers of the file; for a job per channel file), so that a segment analysis can look at one operation instead of the whole program (D67).
- Loop statistics (INTERPRETED): executed blocks per label section, iteration counts, final variable values.
- Channel timeline: estimated time per block aligned at every mark, waiting time per channel per mark.

## 10. Kinematics module contract

The module subscribes to MOTION and CYCLE_CALL, reads the `[[node]]` tree from the machine configuration and the resource state from `Before`/`After`, and computes the pose of the tool tip relative to the current workpiece frame. It publishes `TOOL_POSE` events for analytics. It never writes VM state, never adds or changes an NCX word, and the VM runs completely without it. In the postprocessor picture: the CAM system gives the postprocessor a Cartesian path and a tool vector and the postprocessor computes axis values; here the VM gives axis values and the module computes the Cartesian pose.
